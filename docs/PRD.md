# 커피 주문 앱
## 1. 프로젝트 개요
### 1.1 프로젝트명
커피 주문 앱

### 1.2 프로젝트 목적
사용자가 커피 메뉴를 주문하고, 관리자가 주문을 관리할 수 있는 간단한 풀스택 웹 앱

### 1.3 개발 범위
- 주문하기 화면(메뉴 선택 및 장바구니 기능)
- 관리자 화면(재고 관리 및 주문 상태 관리)
- 데이터를 생성/조회/수정/삭제할 수 있는 기능


## 2. 기술 스택
- 프런트 엔드: HTML, CSS, 리액트, 자바스크립트
- 백엔드: Node.js, Express
- 데이터베이스: PostgreSQL

## 3. 기본사항
- 프런트엔드와 백엔드를 따로 개발
- 기본적인 웹 기술만 사용
- 학습 목적이므로 사용자 인증이나 결제 기능은 제외
- 메뉴는 커피 메뉴만 있음

## 4. 주문하기 화면 PRD
### 4.1 목적 및 사용자
- 목적: 사용자가 커피 메뉴와 옵션을 선택해 장바구니에 담고, 주문을 제출할 수 있게 한다.
- 사용자: 인증 없이 주문하는 일반 사용자
- 이번 문서의 범위: 주문하기 화면의 메뉴 탐색, 옵션 선택, 장바구니 확인 및 주문 제출
- 관리자 화면의 재고·주문 관리 상세 요구사항은 이 범위에 포함하지 않는다.

### 4.2 화면 구성
1. **상단 내비게이션**
   - 브랜드명 `COZY`를 표시한다.
   - `주문하기`와 `관리자` 메뉴를 제공한다.
   - `주문하기` 화면에서는 현재 메뉴가 선택된 상태로 표시된다.
   - `관리자`를 선택하면 관리자 화면으로 이동한다.
2. **메뉴 목록**
   - 주문 가능한 커피를 카드 형태로 표시한다.
   - 각 카드에는 메뉴 이미지, 이름, 기본 가격, 간단한 설명, 추가 옵션 및 `담기` 버튼을 표시한다.
   - 와이어프레임 예시 메뉴: 아메리카노(ICE) 4,000원, 아메리카노(HOT) 4,000원, 카페라떼 5,000원.
   - 와이어프레임의 옵션 예시: 샷 추가(+500원), 시럽 추가(+0원). 메뉴별 제공 옵션은 메뉴 데이터에 따른다.
3. **장바구니**
   - 메뉴 목록 아래에 장바구니를 표시한다.
   - 담긴 메뉴의 이름, 선택 옵션(있는 경우), 수량, 항목별 금액과 전체 주문 금액을 표시한다.
   - 장바구니가 비어 있으면 비어 있음을 알리고, 주문 제출은 할 수 없게 한다.
   - `주문하기` 버튼으로 장바구니의 주문을 제출한다.

### 4.3 기능 요구사항
#### 메뉴 및 옵션
- 메뉴 목록은 백엔드에서 제공하는 메뉴 데이터를 기준으로 표시한다.
- 메뉴별 이름, 설명, 기본 가격, 이미지 및 선택 가능한 옵션을 표시한다.
- 사용자는 메뉴를 장바구니에 담기 전에 카드의 옵션을 선택할 수 있다.
- 옵션의 추가 금액을 메뉴 가격에 반영한다. 추가 금액이 0원인 옵션도 선택 내역에 포함한다.
- 메뉴 목록을 불러오지 못하면 오류 안내를 표시하고, 사용자가 다시 시도할 수 있도록 한다.

#### 장바구니 및 금액
- `담기`를 누르면 현재 선택한 옵션을 포함한 메뉴가 장바구니에 추가된다.
- 항목 금액은 `(기본 가격 + 선택 옵션 추가 금액) × 수량`으로 계산하며, 전체 금액은 항목 금액의 합으로 계산한다.
- 수량이 여러 개인 항목은 수량과 항목 금액을 함께 표시한다.
- 와이어프레임 예시 계산은 아메리카노(ICE) 1개(샷 추가) 4,500원과 아메리카노(HOT) 2개 8,000원, 총 12,500원이다.
- 표시 금액은 원화와 천 단위 구분 기호를 사용한다.

#### 주문 제출
- 장바구니가 비어 있으면 주문 제출을 막는다.
- 제출 중에는 중복 제출을 방지하고 진행 상태를 사용자에게 표시한다.
- 주문이 성공적으로 저장되면 주문 완료 안내를 표시한다.
- 주문 저장에 실패하면 장바구니를 유지하고 오류 안내와 재시도 방법을 제공한다.
- 결제 기능은 제공하지 않는다.

### 4.4 사용자 흐름
1. 사용자가 메뉴와 가격을 확인한다.
2. 원하는 메뉴의 옵션을 선택하고 `담기`를 누른다.
3. 장바구니에서 담긴 메뉴, 옵션, 수량 및 합계를 확인한다.
4. `주문하기`를 눌러 주문을 제출한다.
5. 저장 결과에 따라 완료 안내 또는 오류 안내를 확인한다.

### 4.5 수용 기준
- 메뉴 카드에 이름, 기본 가격, 설명, 제공 옵션 및 담기 버튼이 표시된다.
- 선택한 옵션과 추가 금액이 장바구니 항목 및 합계에 정확히 반영된다.
- 여러 메뉴와 수량의 항목 금액·전체 금액이 정확히 계산된다.
- 와이어프레임 예시 구성에서 전체 금액이 12,500원으로 표시된다.
- 비어 있는 장바구니는 제출할 수 없고, 주문 요청이 진행 중일 때 중복 요청이 발생하지 않는다.
- 주문 성공 및 실패 상황이 사용자에게 구분되어 안내되며, 실패 시 장바구니 내용이 보존된다.

### 4.6 와이어프레임에서 확정되지 않은 항목
- 메뉴별 실제 이미지·설명·목록과 옵션 구성 및 가격은 운영 데이터로 확정한다.
- 장바구니에서 수량 변경·항목 삭제를 제공할지, 동일 메뉴와 옵션을 한 줄로 합칠지는 별도 결정이 필요하다.
- 주문 제출 후 장바구니 초기화 여부와 완료 화면의 구체적인 내용은 별도 결정이 필요하다.
- 품절 메뉴의 노출·담기 제한 및 주문 제출 시 재고 확인 규칙은 관리자 재고 기능과 함께 정의한다.
- 모바일 화면의 카드 배치와 반응형 기준은 별도 UI 설계에서 확정한다.

## 5. 관리자 화면 PRD
### 5.1 목적 및 사용자
- 목적: 관리자가 주문 처리 현황을 확인하고 커피 메뉴별 재고를 조정할 수 있게 한다.
- 사용자: 매장 관리자
- 이번 문서의 범위: 관리자 대시보드, 재고 수량 조정, 주문 현황 확인 및 주문 상태 처리
- 메뉴 등록·수정, 가격 및 옵션 관리 기능은 와이어프레임에 없으므로 범위에 포함하지 않는다.

### 5.2 화면 구성
1. **상단 내비게이션**
   - 브랜드명 `COZY`와 `주문하기`, `관리자` 메뉴를 표시한다.
   - 관리자 화면에서는 `관리자` 메뉴가 현재 선택된 상태로 표시된다.
   - `주문하기`를 선택하면 주문하기 화면으로 이동한다.
2. **관리자 대시보드**
   - 총 주문 수와 상태별 주문 수를 표시한다.
   - 와이어프레임은 총 주문, 주문 접수, 제조 중, 제조 완료 건수를 예시로 보여준다.
3. **재고 현황**
   - 메뉴별 이름과 현재 재고 수량을 카드 형태로 표시한다.
   - 각 카드에 수량을 1개씩 늘리는 `+`와 줄이는 `-` 조작을 제공한다.
   - 와이어프레임 예시 메뉴는 아메리카노(ICE), 아메리카노(HOT), 카페라떼이다.
4. **주문 현황**
   - 주문 시각, 주문 메뉴 및 수량, 주문 금액, 처리 액션을 표시한다.
   - 와이어프레임 예시 행에는 주문 접수 액션 버튼이 표시된다.

### 5.3 기능 요구사항
#### 대시보드
- 대시보드 수치는 저장된 주문 데이터를 기준으로 표시한다.
- 총 주문 수와 상태별 주문 수는 최신 데이터와 일치해야 한다.
- 수치를 불러오지 못한 경우 오류 안내를 표시하고 다시 시도할 수 있게 한다.

#### 재고 관리
- 메뉴별 현재 재고 수량을 백엔드에서 조회해 표시한다.
- `+`를 누르면 해당 메뉴 재고를 1개 증가시키고, `-`를 누르면 1개 감소시킨다.
- 재고는 0개 미만이 될 수 없으며, 0개에서 감소 조작은 비활성화하거나 사용자에게 불가 사유를 안내한다.
- 수량 변경이 저장되는 동안 해당 조작의 중복 요청을 방지하고 진행 상태를 표시한다.
- 저장 성공 시 최신 수량을 표시하고, 실패 시 오류를 안내하며 성공한 것처럼 화면만 갱신하지 않는다.

#### 주문 현황 및 상태 처리
- 주문별 시각, 메뉴명, 수량, 주문 금액과 현재 처리 상태를 표시한다.
- 새 주문의 기본 상태는 `주문 접수`이며, 관리자가 `제조 시작`을 누르면 `제조 중`, `제조 완료`를 누르면 `완료` 상태가 된다.
- 주문 상태 변경은 백엔드에 저장하고, 성공 후 목록과 대시보드 집계에 반영한다.
- 상태 변경에 실패하면 기존 상태를 유지하고 오류 안내 및 재시도 방법을 제공한다.
- 이미 처리 중인 변경의 중복 제출을 방지한다.

### 5.4 사용자 흐름
1. 관리자가 관리자 화면에 진입해 주문 건수와 메뉴별 재고를 확인한다.
2. 필요한 경우 메뉴 카드의 `+` 또는 `-`로 재고 수량을 조정한다.
3. 주문 현황에서 주문 시각, 메뉴, 수량 및 금액을 확인한다.
4. 주문의 처리 액션을 눌러 주문 상태를 갱신한다.
5. 저장 결과가 재고, 주문 목록 및 대시보드에 반영됐는지 확인한다.

### 5.5 수용 기준
- 대시보드에 총 주문 및 상태별 주문 수가 표시되고 저장 데이터와 일치한다.
- 각 메뉴의 현재 재고 수량이 표시되며 `+`와 `-` 조작으로 1개씩 변경할 수 있다.
- 재고는 음수가 되지 않으며, 변경 성공 전에는 새 수량으로 확정 표시하지 않는다.
- 주문 목록의 각 행에 주문 시각, 메뉴와 수량, 금액 및 처리 액션이 표시된다.
- 주문 상태 변경 성공 시 해당 주문 상태와 대시보드 집계가 함께 갱신된다.
- 조회 및 변경 실패 시 사용자에게 오류가 안내되고, 실패한 변경이 성공한 것처럼 표시되지 않는다.

### 5.6 와이어프레임에서 확정되지 않은 항목
- 주문 상태 전이는 `주문 접수` → `제조 중` → `완료`로 한다. 취소 주문 처리 방식은 별도 정의가 필요하다.
- 주문 현황의 정렬 순서, 표시 건수, 과거 주문 조회 및 새 주문 자동 갱신 방식은 별도 결정이 필요하다.
- 주문 생성이 성공할 때 주문 수량만큼 메뉴 재고를 차감한다. 옵션별 재고는 관리하지 않는다.
- 재고 변경에 최대 수량을 둘지, 관리자가 수량을 직접 입력하는 기능을 제공할지는 별도 결정이 필요하다.
- 현 PRD의 기본사항에 따라 인증은 범위에서 제외되어 있으나, 관리자 접근 제한 방식은 배포 전 별도로 검토해야 한다.
- 모바일 화면의 배치와 반응형 기준은 별도 UI 설계에서 확정한다.

## 6. 백엔드 PRD
### 6.1 목적 및 범위
- Node.js와 Express로 프런트엔드와 분리된 API 서버를 구현하고 PostgreSQL에 메뉴, 옵션, 재고, 주문 및 주문 상태를 저장한다.
- 일반 사용자는 메뉴를 조회하고 주문을 제출한다. 관리자는 재고와 주문을 조회하고 재고 및 주문 상태를 변경한다.
- 인증과 결제는 범위에서 제외한다.
- 모든 금액은 원화 정수(원)로 저장하고 반환한다. 브라우저가 제출한 금액은 신뢰하지 않으며, 서버가 데이터베이스의 가격을 기준으로 주문 금액을 계산한다.

### 6.2 데이터 모델
#### `menus` — 메뉴 및 재고
| 필드 | 형식 | 제약 및 설명 |
|---|---|---|
| `id` | `BIGINT` 또는 `UUID` | 기본 키 |
| `name` | `VARCHAR(100)` | 필수, 메뉴명 |
| `description` | `TEXT` | 메뉴 설명 |
| `price` | `INTEGER` | 필수, 0 이상, 원 단위 기본 가격 |
| `image_url` | `TEXT` | 메뉴 이미지 URL, 미등록이면 `NULL` 허용 |
| `stock_quantity` | `INTEGER` | 필수, 0 이상, 기본값 0 |
| `created_at` | `TIMESTAMPTZ` | 필수, 생성 시각 |
| `updated_at` | `TIMESTAMPTZ` | 필수, 수정 시각 |

#### `options` — 메뉴별 선택 옵션
| 필드 | 형식 | 제약 및 설명 |
|---|---|---|
| `id` | `BIGINT` 또는 `UUID` | 기본 키 |
| `menu_id` | `BIGINT` 또는 `UUID` | 필수 외래 키, `menus.id` 참조 |
| `name` | `VARCHAR(100)` | 필수, 옵션명 |
| `price` | `INTEGER` | 필수, 0 이상, 원 단위 추가 금액 |
| `created_at` | `TIMESTAMPTZ` | 필수, 생성 시각 |
| `updated_at` | `TIMESTAMPTZ` | 필수, 수정 시각 |

- 하나의 메뉴는 여러 옵션을 가질 수 있고, 각 옵션은 하나의 메뉴에 속한다.
- 메뉴를 삭제할 때 연결된 옵션의 처리 방식은 데이터 무결성을 지키도록 정한다. 주문 이력이 참조하는 메뉴와 옵션은 주문 기록 보존을 위해 물리 삭제하지 않는다.

#### `orders` — 주문 요약
| 필드 | 형식 | 제약 및 설명 |
|---|---|---|
| `id` | `BIGINT` 또는 `UUID` | 기본 키, 외부에서 주문 조회에 사용 |
| `ordered_at` | `TIMESTAMPTZ` | 필수, 서버가 기록한 주문 일시 |
| `status` | `VARCHAR(20)` 또는 PostgreSQL enum | 필수, `received`, `preparing`, `completed` 중 하나; 기본값 `received` |
| `total_amount` | `INTEGER` | 필수, 0 이상, 서버가 계산한 주문 합계 |
| `created_at` | `TIMESTAMPTZ` | 필수, 생성 시각 |
| `updated_at` | `TIMESTAMPTZ` | 필수, 수정 시각 |

#### `order_items` — 주문 메뉴 항목
| 필드 | 형식 | 제약 및 설명 |
|---|---|---|
| `id` | `BIGINT` 또는 `UUID` | 기본 키 |
| `order_id` | `BIGINT` 또는 `UUID` | 필수 외래 키, `orders.id` 참조 |
| `menu_id` | `BIGINT` 또는 `UUID` | 필수 외래 키, `menus.id` 참조 |
| `menu_name` | `VARCHAR(100)` | 필수, 주문 시점 메뉴명 스냅샷 |
| `quantity` | `INTEGER` | 필수, 1 이상 |
| `unit_price` | `INTEGER` | 필수, 옵션 금액을 포함한 주문 시점 1개 가격 |
| `line_total` | `INTEGER` | 필수, `unit_price × quantity` |

#### `order_item_options` — 주문 시점 옵션 내역
| 필드 | 형식 | 제약 및 설명 |
|---|---|---|
| `id` | `BIGINT` 또는 `UUID` | 기본 키 |
| `order_item_id` | `BIGINT` 또는 `UUID` | 필수 외래 키, `order_items.id` 참조 |
| `option_id` | `BIGINT` 또는 `UUID` | 옵션 식별 외래 키 |
| `option_name` | `VARCHAR(100)` | 필수, 주문 시점 옵션명 스냅샷 |
| `option_price` | `INTEGER` | 필수, 주문 시점 옵션 추가 금액 스냅샷 |

- 주문 항목과 옵션의 이름 및 가격은 주문 당시의 스냅샷으로 보존해 이후 메뉴·옵션 변경이 과거 주문 내역에 영향을 주지 않게 한다.
- 한 주문은 여러 `order_items`를 가지며, 한 주문 항목은 선택한 옵션에 따라 여러 `order_item_options`를 가질 수 있다.
- `orders.total_amount`는 모든 주문 항목의 `line_total` 합과 같아야 한다.
- 외래 키의 ID 형식은 프로젝트의 PostgreSQL 마이그레이션에서 `BIGINT` 또는 `UUID` 하나로 통일한다.

### 6.3 데이터 스키마를 위한 사용자 흐름
1. 주문 화면 진입 시 브라우저가 메뉴 조회 API를 호출한다. 서버는 주문 가능한 메뉴와 메뉴별 옵션을 반환하며, 재고 수량은 일반 사용자 응답에 포함하지 않는다.
2. 관리자 화면 진입 시 관리 API로 메뉴와 현재 재고, 주문 목록 및 대시보드 집계를 조회한다.
3. 사용자가 메뉴와 옵션, 수량을 선택하면 선택 내용은 장바구니에 표시된다. 장바구니 내용은 주문 제출 전까지 브라우저에서 관리한다.
4. 사용자가 `주문하기`를 선택하면 메뉴 ID, 수량, 선택 옵션 ID를 서버에 제출한다. 서버는 입력과 재고를 검증하고 데이터베이스 가격으로 금액을 계산한 뒤, 주문·주문 항목·옵션 스냅샷 저장과 재고 차감을 하나의 데이터베이스 트랜잭션으로 처리한다.
5. 주문 저장이 성공하면 주문 기본 상태는 `received`(화면 표시 `주문 접수`)가 되고, 브라우저는 주문 ID를 포함한 완료 응답을 받는다. 실패하면 주문과 재고 변경을 모두 롤백하고 오류 응답을 반환한다.
6. 관리자의 주문 현황은 저장된 주문과 항목 정보를 표시한다. 관리자가 `제조 시작`을 요청하면 상태를 `preparing`(화면 표시 `제조 중`)으로, `제조 완료`를 요청하면 `completed`(화면 표시 `완료`)로 변경한다.
7. 메뉴 재고 변경 요청은 관리 API가 데이터베이스에 저장한 후 최신 수량을 반환한다. 변경 실패 시 재고를 성공한 것처럼 갱신하지 않는다.

### 6.4 API 설계
모든 요청·응답 본문은 JSON을 사용하며, 경로는 `/api`를 기준으로 한다.

#### 메뉴 조회
- `GET /api/menus`: 주문 화면용 메뉴 목록과 옵션을 조회한다. `id`, `name`, `description`, `price`, `imageUrl`, `options`를 반환하고 재고 수량은 반환하지 않는다.
- `GET /api/admin/menus`: 관리자용 메뉴 목록을 조회하며 메뉴 정보와 `stockQuantity`를 반환한다.

#### 주문 생성 및 조회
- `POST /api/orders`: 주문을 생성한다.
  - 요청 예시:
    ```json
    {
      "items": [
        {
          "menuId": "menu-id",
          "quantity": 2,
          "optionIds": ["option-id"]
        }
      ]
    }
    ```
  - 서버는 메뉴·옵션의 존재와 연결 관계, 양의 정수 수량, 재고 충분 여부를 검증한다. 단가와 합계를 서버에서 계산하고 주문 및 세부 항목을 저장한 후 재고를 차감한다.
  - 성공 시 `201 Created`와 주문 ID, 서버 계산 금액, 상태 및 주문 시각을 반환한다.
- `GET /api/orders/:orderId`: 주문 ID에 해당하는 주문 시각, 상태, 메뉴명, 수량, 주문 당시 옵션과 금액을 조회한다. 없으면 `404 Not Found`를 반환한다.
- `GET /api/admin/orders`: 관리자 주문 현황용 주문 목록을 조회한다. 각 주문의 시각, 상태, 메뉴·수량·옵션, 금액을 반환하며 최신 주문 우선으로 정렬한다.
- `PATCH /api/admin/orders/:orderId/status`: 주문 상태를 다음 단계로 변경한다. 요청 본문은 `{ "status": "preparing" }` 또는 `{ "status": "completed" }`이며, 허용된 전이만 저장한다. 주문접수에서 완료로 바로 건너뛰거나 완료 상태를 다시 변경할 수 없다.

#### 재고 변경 및 대시보드
- `PATCH /api/admin/menus/:menuId/stock`: 재고를 지정한 증감 수량만큼 변경한다.
  - 요청 본문 예시: `{ "adjustment": -1 }` 또는 `{ "adjustment": 1 }`.
  - 증감량은 0이 아닌 정수여야 하며, 결과 재고가 음수가 되면 변경을 거부한다. 성공 시 최신 `stockQuantity`를 반환한다.
- `GET /api/admin/dashboard`: 총 주문 수와 상태별(`received`, `preparing`, `completed`) 주문 수를 반환한다. 집계 기준은 저장된 주문이며 상태별 합계는 총 주문 수와 일치한다.

#### 공통 오류 응답 및 규칙
- 오류 본문은 `{ "error": { "code": "ERROR_CODE", "message": "설명" } }` 형식으로 반환한다.
- `400 Bad Request`: 잘못된 JSON, 필수 필드 누락, 유효하지 않은 수량·옵션, 허용되지 않은 상태 전이.
- `404 Not Found`: 존재하지 않는 메뉴, 주문 또는 옵션.
- `409 Conflict`: 재고 부족 등 현재 데이터 상태 때문에 주문 또는 변경을 처리할 수 없음.
- `500 Internal Server Error`: 예상하지 못한 서버 오류. 내부 스택과 데이터베이스 세부 정보는 응답에 노출하지 않는다.
- 금액은 모두 0 이상의 정수 원 단위로 반환한다. 날짜·시각은 시간대가 포함된 ISO 8601 형식으로 반환한다.
- 재고 차감과 주문 기록 저장은 단일 트랜잭션으로 처리해 일부만 반영되는 상태를 방지한다. 동시 주문으로 재고가 부족해질 수 있는 경우에도 재고가 음수가 되지 않도록 잠금 또는 조건부 갱신을 사용한다.

### 6.5 백엔드 수용 기준
- 주문 메뉴 조회 응답에는 메뉴와 연결된 옵션이 포함되고 일반 사용자 응답에 재고 수량은 포함되지 않는다. 관리자 메뉴 조회 응답에는 재고 수량이 포함된다.
- 주문은 서버가 계산한 메뉴·옵션 가격으로 저장되며, 요청에 임의 금액을 포함해도 주문 금액에 반영되지 않는다.
- 재고가 충분한 주문은 주문·항목·옵션 스냅샷을 저장하고 주문 수량만큼 재고를 차감한다. 재고 부족 또는 저장 오류 시 주문과 재고가 함께 롤백된다.
- 신규 주문 상태는 `received`이고, 상태 API는 `received` → `preparing` → `completed` 순서만 허용한다.
- 주문 ID로 주문 시각, 상태, 메뉴, 수량, 옵션 및 금액을 조회할 수 있다.
- 재고는 API를 통한 주문·관리 변경 후에도 음수가 되지 않으며, 재고 변경 응답에는 저장된 최신 수량이 포함된다.
- 대시보드 총 주문 수와 세 상태의 집계가 저장된 주문 데이터와 일치한다.
